# 부정행위 탐지 구조

## 왜 바꿨나

기존 구조는 원시 로그를 그대로 쌓았다.

- `typing_results`: 점수가 적립될 때마다 1행. 행 수가 **완료한 문장 수**에 비례해 무한히 늘어난다. 그런데 랭킹은 `monthly_stats`만 읽는다.
- `suspicious_records`: Firestore 시절 구조 그대로. `record_data`에 문장 본문까지 들어 있다.
- 판정 로직이 전부 클라이언트에 있어서 우회가 쉽다.

## 새 구조

행 수가 **세션 수**에만 비례하도록 바꿨다.

| 테이블 | 행이 생기는 단위 | 대략적인 증가량 |
|---|---|---|
| `typing_sessions` | 사용자 × 탭 세션 | 하루 활성 사용자당 1~3행 |
| `abuse_signals` | 사용자 × 세션 × 룰, 룰에 걸렸을 때만 | 정상 사용자는 0행 |

`typing_sessions`에는 합계·제곱합·카운터만 들어간다. 문장 본문도, 키 입력 시각도 저장하지 않는다. 제곱합을 같이 두는 이유는 원시 값 없이도 서버가 평균과 표준편차를 복원하기 위해서다.

### 재전송에 안전한 이유

클라이언트는 **세션 시작부터의 누적 스냅샷**을 보내고, 서버는 `greatest()`로 덮어쓴다. 전송이 실패하거나 중복돼도 집계가 어긋나지 않는다. 그래서 클라이언트에 재시도 큐가 없다.

## 탐지 룰

`evaluate_session_signals()` — 클라이언트가 올린 집계 기준.

| 룰 | 심각도 | 판정 근거 |
|---|---|---|
| `NO_IME_COMPOSITION` | 3 | 한글 문장 5개 이상인데 IME 조합 이벤트가 20% 미만. 사람 손으로는 나올 수 없다 |
| `NO_KEY_EVENTS` | 3 | 문장 10개 이상 완료했는데 키 이벤트가 타수의 1/4 미만. 값이 직접 주입되고 있다 |
| `BACKGROUND_INPUT` | 3 | 창이 포커스를 잃은 상태에서 입력 10회 이상 |
| `UNIFORM_KEY_RHYTHM` | 3 | 키 간격 2백 회 이상 표본에서 변동계수 0.15 미만 |
| `NO_CORRECTION` | 2 | 문장 20개 이상, 백스페이스 0회, 평균 정확도 99% 이상 |
| `SPEED_SPIKE` | 2 | 최고 1200 CPM 초과 + 평균 정확도 98% 이상 |
| `FLAT_CPM_VARIANCE` | 2 | 문장 5개 이상에서 CPM 표준편차 50 미만 + 평균 정확도 95% 이상 (원본 타입뉴스 룰) |
| `PASTE_ATTEMPT` | 1 | 붙여넣기 시도 5회 이상 |
| `MARATHON_SESSION` | 1 | 세션 5시간 이상 + 평균 정확도 95% 이상 (원본 타입뉴스 룰) |

`evaluate_server_side_signals()` — **클라이언트가 조작할 수 없는** 신호.

| 룰 | 심각도 | 판정 근거 |
|---|---|---|
| `UNIFORM_SUBMIT_INTERVAL` | 3 | 최근 2시간 점수 적립 시각의 간격 변동계수가 0.12 미만. `typing_results.created_at`은 서버가 찍으므로 위조가 불가능하다 |

`record_typing_result()` — 점수 제출 자체의 **물리적 타당성**. 자세한 근거는 [scoring.md](scoring.md).

| 룰 | 심각도 | 판정 근거 |
|---|---|---|
| `IMPLAUSIBLE_SCORE` | 3 | 한 문장 600타 초과. 실측 최대는 장문 277타 |
| `IMPLAUSIBLE_ELAPSED` | 3 | 소요 시간 0.5초 미만 또는 1시간 초과 |
| `IMPOSSIBLE_SPEED` | 3 | 초당 20타(1200 CPM) 초과 |
| `HOURLY_SCORE_CAP` | 3 | 1시간 누적 60,000점 초과 |

이 룰에 걸리면 점수가 반영되지 않고 신호만 남는다.

클라이언트 집계는 마음만 먹으면 위조할 수 있다. 그래서 서버 시각 기반 룰을 함께 둔다. 클라이언트 신호를 완벽히 지우면 `NO_KEY_EVENTS`에, 그럴듯하게 위조하면 서버 시각 룰에 걸리도록 설계했다.

## 관리자 연동

```sql
-- 위험도 순 워치리스트. 관리자가 아니면 빈 결과가 나온다.
select * from get_abuse_watchlist(p_since_days => 30, p_limit => 50);

-- 확인 처리. 일주일간 다시 올라오지 않는다.
select review_abuse_signals(p_profile_id => '...', p_note => '수동 확인, 정상');
```

`risk_score`는 `심각도² × (1 + ln(반복횟수))`의 합이다. 심각도가 높을수록 크게 반영하고, 반복 횟수는 로그로 눌러서 한 세션이 순위를 독식하지 않게 했다.

탐지 결과는 **본인도 조회할 수 없다.** 어떤 룰에 걸렸는지 알면 회피가 쉬워지기 때문에 RLS를 관리자 전용으로 뒀다.

## 보존 정책

```sql
select public.prune_integrity_data();  -- 기본값: 세션 120일, 확인 완료된 신호 400일
```

신호가 붙은 세션은 근거로 남겨야 하므로 지우지 않는다. pg_cron으로 하루 한 번 도는 것을 권장한다.

```sql
select cron.schedule('prune-integrity', '20 4 * * *', $$select public.prune_integrity_data()$$);
```

## 남은 과제

- `typing_results`는 여전히 문장마다 1행씩 쌓인다. 이벤트가 진행 중이라 손대지 않았다. 이벤트 종료 후 보존 기간(예: 90일)을 정하는 것을 권한다. 서버 시각 룰이 최근 2시간만 보므로 오래된 행은 탐지에 쓰이지 않는다.
- `suspicious_records`는 Firestore 이관 데이터 보관용이다. 검증이 끝나면 삭제 가능하다.
