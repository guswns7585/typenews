> ⚠️ **PostgREST는 한 응답에 1,000행까지만 준다(`db-max-rows`).**
> `limit`을 크게 줘도 서버가 자르는데, **요청은 성공한다.** 이 스크립트가 처음에
> 478문장을 `undefined`로 받아 "불일치 7,648건"을 냈다. 7,648 = 478 × 16조합.
> 같은 함정이 `sentence-picker.ts`에도 있었다(`.limit(2000)`). 지금은 가장 큰 묶음이
> 433문장이라 무해했지만, 관리자 화면에서 문장을 추가하다 1,000을 넘기면 그 뒤
> 문장이 영영 안 나오게 된다. 둘 다 페이징으로 고쳤다.
>
> RPC(POST)에는 `Range` 헤더가 먹지 않는다. 같은 페이지가 계속 와서 무한 루프가 된다.
> 집합을 돌려주는 함수는 쿼리 파라미터 `?limit=&offset=`을 쓴다.

**섀도인 이유** — 한 글자라도 다르게 세면 정직한 사용자 전원의 점수가, 그것도
이벤트 진행 중에 어긋난다. 그래서 지금은 계산하고 기록만 하고 적립은 클라이언트
값 그대로다. 워치리스트에는 "옮기다 틀린 것"으로 설명되지 않는 크기
(기대값의 2배 이상 **그리고** 50타 초과)만 `SCORE_MISMATCH`로 올린다.

**검산되지 않는 것** — 단어 모드(10개 묶음이라 문장 번호가 하나로 정해지지 않음),
뉴스 모드(RSS라 DB에 원문이 없음), JSON 폴백으로 뽑힌 문장. `unverified`로만 센다.

**전환 판단** — 일주일 뒤 아래로 확인한다. `mismatched`가 며칠째 0이면 전환한다.
전환 방법은 `0024` 파일 맨 아래에 적어뒀다.

```sql
select * from get_score_verification_summary(14);
```

### 적용 순서 ⚠️

`0024`는 7-인자 `record_typing_result`를 drop하고 9-인자로 바꾼다. `0014` 때와 같은
상황이라 같은 방식으로 막아뒀다.

- **새 클라이언트 + 구 서버** → 9-인자 실패 → `items` → `base`로 한 단계씩 내려가 성공
- **새 클라이언트 + 새 서버** → 바로 성공
- **구 클라이언트 + 새 서버** → 7-인자 호출을 새 함수의 기본값이 받는다. 점수를 잃지 않는다

즉 **어느 쪽을 먼저 해도 점수를 잃지 않는다.** 다만 프론트엔드를 배포하기 전에는
모든 제출이 `unverified`로만 쌓이므로 검산이 시작되지 않는다.

### 8. 헤더 기록 — ✅ `0029` + `header-stats.tsx`

운영자가 화면에서 직접 발견한 것 둘.

**(1) 로그아웃 상태에서도 숫자가 보였다.** 기록은 계정에 쌓이는 것이라 로그인하지
않으면 아무 의미가 없는데, 이 브라우저에 남은 값이 그대로 보이고 있었다.

| 칸 | 로그아웃일 때 무엇이 보였나 |
|---|---|
| 누적 문장 | `summary ?? sessionCount` — 이번 세션에 친 개수 |
| 최고 CPM | localStorage의 `maxCpm` |
| 이번 달 점수 | localStorage의 `monthlyScore` |

`SIGNED_OUT`에서는 `resetRecords()`가 지우고 있었지만, **한 번도 로그인한 적 없는
방문자**는 그 경로를 타지 않는다. 이제 로그인 여부를 직접 보고 `—`를 띄운다.
0으로 채우지 않는 이유는 그것이 "기록이 없다"는 또 다른 거짓말이기 때문이다.
읽는 중일 때도 `—`다 — 0을 먼저 띄우면 번쩍였다가 튄다.

**(2) 누적 문장에 단어 모드가 섞였다.** 단어 10개 묶음이 "1문장"으로 세어져서,
문장을 한 개도 안 쳐도 누적 문장이 올라갔다.

`typing_mode_counts`로 다시 세는 것이 맞아 보이지만 **데이터가 허락하지 않는다.**

```
profiles.total_typing_count 합계 : 2,430,611
typing_mode_counts 제출 수 합계  :       163
기록이 있는 838명 중 837명이 모드별 집계가 아예 없음 (전부 Firestore 이관분)
```

갈아타면 837명이 하루아침에 "0문장"이 된다. 그래서 이관분은 그대로 두고
**앞으로 단어 모드가 이 값을 올리지 않게** 했다(`0029`). 과거의 단어 몫은 이관 값
안에 섞인 채 남는다 — 떼어낼 방법이 없다. 단어 개수는 헤더 툴팁에서 따로 보여준다.

### 7. 점수 유실 + 중복 적립 — ✅ `0028` + 재전송 큐 (외부 검수 1·3번)

두 문제가 한 작업으로 풀린다. **재전송을 만들려면 서버가 "이건 아까 그거다"를
알아야 하고, 그 장치가 곧 중복 적립을 막는 장치이기 때문이다.**

| 어디 | 내용 |
|---|---|
| `0028` | `typing_results.submission_key` + 부분 유니크 `(profile_id, submission_key)` |
| `0028` | `record_typing_result`에 `p_submission_key`. 같은 키는 조용히 성공으로 끝낸다 |
| [score-outbox.ts](../frontend/features/scoring/score-outbox.ts) | localStorage 대기열 |
| `typing-workspace.tsx` | **담고 나서 보낸다.** online·visible·1분마다 재전송 |

**순서가 핵심이다.** 보내고 실패하면 담는 방식은, 다 치고 바로 탭을 닫는 흔한
경우에 그 코드가 아예 돌지 않아 점수를 잃는다. `localStorage`는 동기라 `enqueue`에서
돌아온 시점에는 이미 저장돼 있다. 단어 묶음을 비우기 전에 담기는 것도 이걸로 해결된다.

정한 것 둘:

- **달이 바뀐 대기 항목은 버린다.** 서버는 적립 시점의 달로 점수를 넣으므로,
  7월에 친 점수를 8월에 보내면 8월 랭킹에 들어간다. 경품이 달마다 걸리는 구조에서
  그것은 점수를 잃는 것보다 나쁘다
- **로그인하지 않고 친 점수는 버린다**(`Not authenticated`는 재시도하지 않는다).
  예전에도 적립되지 않았고, 남겨두면 나중에 로그인하는 순간 갑자기 쌓인다.
  JWT 만료(`PGRST301`)는 여기 해당하지 않는다 — 토큰이 갱신되면 성공한다

동작 확인은 실제 모듈로 한다 (네트워크·DB 없음, 24개 검사):

```bash
npx tsx scripts/test-score-outbox.mts
```

⚠️ `0028`은 9-인자 `record_typing_result`를 drop하고 10-인자로 바꾼다. 클라이언트에
4단계 폴백(`key` → `verify` → `items` → `base`)이 있어 어느 쪽을 먼저 해도 점수를
잃지 않는다.

### 6. 만료 당첨자 복원 버그 — ✅ `0027` (외부 검수 지적)

`mark_winner_responded`가 `status in ('pending','expired')`이면 무조건 `confirmed`로
바꿨다. `expired`를 허용한 것 자체는 이유가 있다 — 기한 직전에 메일로 주소를 보낸
사람을 살려주기 위해서다.

문제는 **만료 뒤에는 재추첨이 돌아 그 경품에 새 주인이 생긴다**는 점이다.
그 상태에서 옛 당첨자의 "메일로 받음"을 누르면 경품 하나에 당첨자가 둘이 된다.
`prize_winners`의 유니크는 `(month_id, profile_id)`라 이것을 막지 못한다 —
같은 경품을 두 사람이 갖는 것은 제약에 걸리지 않는다.

| 어디 | 내용 |
|---|---|
| `0027` | 되살리려는 경품에 `pending`/`confirmed`인 다른 당첨자가 있으면 거절 |
| `0027` | `get_prize_winners`에 `prize_taken` 컬럼 추가 (반환 타입이 바뀌어 drop 후 재생성) |
| `winners-tab.tsx` | 그런 행에는 "메일로 받음" 버튼을 띄우지 않고 `재추첨됨` 배지를 보여준다 |

막기만 하고 방법을 안 주면 운영이 막히므로, **정말 옛 당첨자에게 주려면 새 당첨자를
먼저 취소하면 된다.** 예외 메시지에 그 방법과 상대 닉네임을 함께 넣었다.

### 9. 단어·뉴스 서버 점수 강제 — 구현 완료, `0033` 적용부터 대기

- 단어 다이얼 큐가 문자열 대신 `sentences.id`를 유지하고, 10개 묶음에 각 단어 ID와

- `/api/news`가 허용된 SBS·BBC RSS를 서버에서 파싱·정규화하고 원문을

- JSON 폴백은 화면상 성공과 서버 미적립이 어긋나므로 제거했다. DB 원문을 못 읽으면
  명확한 로딩 오류를 보여준다.
- RSS 허용 목록은 경로뿐 아니라 SBS 섹션 쿼리까지 고정했고 2MB 상한을 유지한다.

- Vercel Production에 로컬 값을 사용해 `SUPABASE_SERVICE_ROLE_KEY`를 Sensitive로
  등록했다. 키 값은 출력하거나 소스에 넣지 않았다.
